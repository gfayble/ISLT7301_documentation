# ISLT7301_documentation

Documentation for the Fall 2026 Semester of MU's ISLT 7301 class.

## Who should use this branch for commits.

Note that this is a branch from the main repository. It is meant for contribution by students participating in the Fall 2026 sections of ISLT7301.

## What to include in this branch

This branch is for documenting our exploration of issues, insights gained, lessons learned, epiphanies, and explanations, etc., for creating Ubuntu 24.04-based LAMP servers in Fall 2026. Open source code is live and changes, and between the time any issue has arisen and a solution has been found, the variables at play can be quite complex. What we will create is a snapshot of our experiences with different versions of Ubuntu, Apache2, MySQL, and PHP as they interact for using WordPress, Omeka, and Koha.

## How to format your work

As with all git pages, the default formatting is Markdown. I recommend the [Markdown Guilde's Markdown Cheat Sheet](https://www.markdownguide.org/cheat-sheet/) as a quick reference.

When including screenshots, please upload the screenshot to the [Fall 2026 Branch images directory[(https://github.com/imparseable/ISLT7301_documentation/tree/Fall2026/images). To include the inline image, use the format `![Alt text describing the image](https://linktoimage.ext "Title of the Image")`.

### When creating a page be sure to include

1. The version of each program you are using (e.g. `php -v`)
2. A description of the problem you are experiencing. If you are using screenshots, **please anonymize any personally identifiable information (including your gCloud ID!)**. If it took time to figure out what the problem actually was, please describe that process!
3. The solution you implemented, including *in-text links* with descriptive text, (e.g. [the WordPress and PHP compatibility page recommends PHP version 8.3 minimum for WordPress versions 6.8 and 6.9](https://make.wordpress.org/core/handbook/references/php-compatibility-and-wordpress-versions/)).
4. Any possible other solutions based on what you learned from fixing a problem.
5. Any other information that is relevant, or required to fix the problem.

Including `code` is helpful, and full paths *and* abbreviated paths may be used to clarify where in the directory structure and which files or settings were changed.
